# Публикация и подключение заказов

## Текущее назначение

Проект — статическая демонстрация UX/UI ресторана «Чаван Чуду» для GitHub Pages. Для работы не нужен сервер приложения. Поиск, выбор блюд и пересчёт корзины выполняются в браузере.

Демонстрация не отправляет заказы в ресторан, не резервирует блюда и время, не списывает деньги. Успех в демонстрационном сценарии не означает, что ресторан принял заказ. В интерфейсе это должно быть обозначено явно.

Телефон, адрес доставки, имя и комментарий посетителя нельзя сохранять в `localStorage`, `sessionStorage`, URL, аналитике или журналах. Если они используются для демонстрации формы, они остаются только в текущем состоянии страницы и не передаются внешнему сервису. Данные банковских карт не запрашиваются. Локально допустимо хранить только неперсональные настройки и состав корзины.

## Проверка и сборка

Используйте Node.js 22. В проекте нет внешних npm-зависимостей, поэтому отдельный шаг установки не требуется.

```sh
npm test
npm run check
npm run build
```

Публикуемая папка — `dist/`. В неё должны попадать только файлы интерфейса и необходимые публичные ресурсы. Сохранённые ответы исходного сайта, временные файлы, документация разработки, служебные токены и исходные данные аудита не должны включаться в публикацию.

Ресурсы должны открываться по относительным путям, чтобы проект работал в подпапке `/Chavan/`. Не добавляйте `CNAME`, если перенос на собственный домен не согласован отдельно.

## Настройка GitHub Pages

1. Откройте [репозиторий general-fox/Chavan](https://github.com/general-fox/Chavan).
2. В **Settings → Pages → Build and deployment** выберите источник **GitHub Actions**.
3. Убедитесь, что GitHub Actions разрешены в настройках репозитория и окружение `github-pages` допускает публикацию из `main`.
4. Отправьте изменения в `main` либо запустите **Actions → Deploy GitHub Pages → Run workflow** для этой ветки.
5. Дождитесь успешных задач `build` и `deploy`. Итоговый адрес находится в окружении `github-pages` и результате задачи публикации.

Ожидаемый адрес без собственного домена: [https://general-fox.github.io/Chavan/](https://general-fox.github.io/Chavan/). Наличие workflow само по себе не означает, что сайт уже опубликован.

Workflow использует Node.js 22, затем последовательно выполняет проверки и сборку. Только `dist/` передаётся в Pages. Сборка получает права чтения репозитория и настроек Pages; задача публикации — `pages: write` и `id-token: write`. Личный токен для штатной публикации не нужен: используется временный `GITHUB_TOKEN`. Текущая публикация не отменяется при появлении следующей.

Версии действий сверены с официальными источниками 26 октября 2026 года: [checkout v7](https://github.com/actions/checkout/releases/tag/v7.0.1), [setup-node v7](https://github.com/actions/setup-node/releases/tag/v7.1.0), [configure-pages v5, upload-pages-artifact v4 и deploy-pages v4](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages).

## Что потребуется для реальных заказов

1. **Подключение к ресторану.** Получить документированный API действующей системы заказов, отдельный тестовый доступ и согласованный способ приёма заказа кухней. Публичные параметры старого сайта не использовать как разрешение на интеграцию.
2. **Проверка каталога на сервере.** Перед подтверждением сервер заново проверяет цены, скидки, доступность, количество и итог. Сумме, присланной браузером, доверять нельзя.
3. **Доставка и самовывоз.** Рассчитывать доступность адреса, цену, минимум, порог бесплатной доставки и время через рабочие правила ресторана. Неизвестные условия не заменять нулевой ценой. Уточнить конфликт времени работы, описанный в [UX-аудите](UX-AUDIT.md).
4. **Создание заказа.** Отправлять запрос через собственный сервер или согласованный шлюз, возвращать номер и подтверждённый статус. Повторное нажатие или сетевой повтор не должны создавать дубликат. Ошибку отображать без очистки корзины.
5. **Оплата.** Использовать размещённую форму платёжного провайдера. Создание платежа и проверка подписанных уведомлений выполняются сервером. Не хранить секреты и карточные данные в статическом проекте.
6. **Данные клиента.** Определить необходимые поля, сроки хранения, доступ сотрудников и тексты согласий для рабочего сервиса. Передавать сведения только выбранным сервисам по защищённому соединению, исключить их из аналитики и технических журналов.
7. **Приёмочные проверки.** Проверить тестовый заказ, недоступное блюдо, адрес вне зоны, закрытую кухню, отклонённую оплату, повторный запрос и получение заказа рестораном. После проверки заменить демонстрационные сообщения на реальные статусы.

GitHub Pages размещает статические файлы; серверную часть заказов и платёжные секреты необходимо размещать отдельно. Адрес API можно публиковать в конфигурации интерфейса, секретный ключ — нельзя.
